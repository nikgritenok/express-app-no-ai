# express-app

Стартер для JS-backend хакатона: Express 5, строгий TypeScript, Vitest, Zod, PostgreSQL 17 и Prisma ORM 7.10.1. Шаблоны Pug и существующие HTTP-ответы сохранены.

## Какой способ запуска выбрать

- **Через Docker Compose:** установите Git и Docker. Node.js, pnpm и зависимости установятся внутри образа; на компьютере они не обязательны.
- **Локально:** установите Git, Node.js 24 LTS и pnpm 12.14.0. Нужен доступ к PostgreSQL: через Docker Compose либо собственный PostgreSQL. Для подсказок типов в редакторе установите зависимости и выполните `pnpm db:generate`.

Первую установку и запуск каждый участник должен выполнить **до хакатона**: для скачивания инструментов, образов и пакетов нужен интернет.

## 1. Установить Git

Официальная страница: [установка Git](https://git-scm.com/install/).

- **Windows:** скачайте установщик Git for Windows с официальной страницы, установите с доступом к Git из командной строки и заново откройте терминал. Команды проекта можно выполнять в PowerShell.
- **macOS:** установите Git по инструкции для macOS на официальной странице. Один из вариантов — выполнить `xcode-select --install` и завершить установку Command Line Tools в открывшемся окне.
- **Ubuntu / Debian:** выполните:

  ```sh
  sudo apt update
  sudo apt install git
  ```

- **Другой Linux:** выберите свой дистрибутив на официальной странице установки Git.

Проверьте установку:

```sh
git --version
```

Перед первым коммитом настройте своё имя и email командами `git config --global user.name` и `git config --global user.email`, передав им свои значения.

## 2. Установить Docker — для контейнерного запуска

Для Windows и macOS проще использовать **Docker Desktop**: в него уже входят Docker Engine и Docker Compose. Устанавливать старую отдельную утилиту `docker-compose` не нужно; команды ниже используют `docker compose`.

- **macOS:** откройте [официальную инструкцию](https://docs.docker.com/desktop/setup/install/mac-install/), скачайте вариант для Apple Silicon или Intel, перенесите Docker в Applications и запустите Docker Desktop.
- **Windows:** откройте [официальную инструкцию](https://docs.docker.com/desktop/setup/install/windows-install/), проверьте требования к системе и установите Docker Desktop с backend WSL 2. Если WSL ещё нет, выполните `wsl --install` в PowerShell от администратора и перезагрузите компьютер, если потребуется. Нужна включённая аппаратная виртуализация. Используйте Linux containers.
- **Linux:** установите [Docker Desktop для своего дистрибутива](https://docs.docker.com/desktop/setup/install/linux/) либо [Docker Engine](https://docs.docker.com/engine/install/) вместе с [Compose plugin](https://docs.docker.com/compose/install/linux/). Docker Desktop требует поддержки KVM. При выборе Engine следуйте официальной инструкции настройки доступа: не выдавайте всем права на Docker socket.

После установки **запустите Docker Desktop и дождитесь запуска Engine**. Если используете Docker Engine на Linux, должен быть запущен его сервис.

Проверьте:

```sh
docker --version
docker compose version
docker info
docker run --rm hello-world
```

`docker info` должен показывать работающий сервер без ошибки подключения. Установка только Docker CLI недостаточна.

## 3. Получить проект

Склонируйте репозиторий через `git clone`, указав адрес репозитория команды, и откройте полученный каталог в терминале и редакторе. Адрес можно скопировать на странице репозитория у вашего Git-хостинга. Все дальнейшие команды выполняются из каталога с `package.json` и `compose.yaml`.

## Настроить окружение

Скопируйте безопасный пример `.env.example` в `.env`.

macOS / Linux:

```sh
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Команду копирования выполняйте один раз: повторное копирование перезапишет ваши настройки. Сам файл `.env` необязателен, но для запуска сервера обязателен `DATABASE_URL`: задайте его в окружении или в `.env`. Настоящий `.env` исключён из Git и Docker build context; коммитится только `.env.example`. Учётные данные PostgreSQL в примере публичные, только для локальной разработки; для production нужны отдельные секреты.

| Переменная           | По умолчанию                             | Назначение                                                                                                          |
| -------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `PORT`               | `3000`                                   | Целое десятичное число от 0 до 65535; в Compose используйте 1–65535. Локально 0 позволяет ОС выбрать свободный порт |
| `HOST_PORT`          | `3000`                                   | Внешний порт Docker Compose; локальный Node.js его не использует, Zod его не проверяет                              |
| `NODE_ENV`           | `development`                            | Только `development`, `test` или `production`; финальный Docker-образ по умолчанию использует `production`          |
| `DEBUG`              | `express-app:server` в примере и Compose | Пространства имён для отладочных сообщений сервера; `DEBUG=` отключает их                                           |
| `DATABASE_URL`       | Нет; обязателен для сервера и миграций   | URL с протоколом `postgresql://` или `postgres://`; пример локального подключения находится в `.env.example`        |
| `POSTGRES_HOST_PORT` | `5432`                                   | Порт локального PostgreSQL в Compose, опубликованный только на `127.0.0.1`; Node.js его не использует               |

До создания HTTP-сервера Zod проверяет `PORT`, `NODE_ENV`, `DEBUG` и `DATABASE_URL` по схеме в `src/config.ts`. Значения по умолчанию применяются только к отсутствующим переменным, а не к пустым строкам. `PORT=3000oops`, дробные числа, пробелы, отрицательные числа, значения выше 65535 и пустой `PORT` отклоняются; пустой или неизвестный `NODE_ENV` тоже недопустим. `DEBUG=` допустим. Отсутствующий или некорректный `DATABASE_URL` отклоняется без вывода его значения. После валидации сервер подключается к БД и только затем открывает HTTP-порт; `SIGINT`/`SIGTERM` закрывают HTTP-сервер и клиент БД.

При ошибке серверный процесс завершается с кодом 1 до открытия порта; в stderr попадают только названия невалидных полей, без их значений и содержимого `.env`. `pnpm dev` может остаться в watch-режиме после ошибки дочернего процесса: исправьте `.env` и перезапустите команду. Compose может отклонить некорректную настройку порта раньше, при разборе port mapping.

**Локально:** `pnpm dev` и `pnpm start` загружают `.env` встроенным механизмом Node.js `--env-file-if-exists`. Переменные, уже заданные в терминале или хостинге, имеют приоритет над файлом. Если `DEBUG` нигде не задан, отладочные сообщения выключены. После изменения `.env` перезапустите сервер: watch следит за исходниками, а не за конфигурацией.

**В Compose:** `.env` используется для подстановки настроек и как необязательный `env_file` приложения. Для `PORT`, `NODE_ENV` и `DEBUG` приоритет: окружение терминала → `.env` → значения в Compose. `HOST_PORT` и `POSTGRES_HOST_PORT` управляют публикацией портов. `DATABASE_URL` в сервисах `app` и `migrate` явно указывает на внутренний сервис `db`, поэтому локальный URL с `127.0.0.1` из `.env` туда не переносится. Compose предназначен только для локальной БД с публичными примерными учётными данными. Для собственного PostgreSQL используйте локальный запуск или production-образ с отдельным `DATABASE_URL`. Необходим Docker Compose 2.24 или новее.

Например, если на компьютере занят порт 3000, измените только `HOST_PORT=3001`. Docker-приложение откроется на `http://localhost:3001`, продолжая слушать `PORT=3000` внутри контейнера. Для локального запуска другой порт задаётся через `PORT`, а не `HOST_PORT`.

После изменения `.env` для Docker выполните:

```sh
docker compose up --detach --force-recreate
```

`pnpm test`, `pnpm test:watch` и `pnpm verify` не загружают `.env` или `.env.test`, включая переменные с префиксом `VITE_`: автозагрузка отключена через `envDir: false` в `vitest.config.ts`. Переменные уже запущенного процесса по-прежнему наследуются; тесты схемы передают явные входные данные и не меняют `process.env`. При добавлении новой переменной обновляйте схему, `.env.example` и эту инструкцию; секреты передавайте отдельно.

## 4. Запустить через Docker Compose

```sh
docker compose up --build
```

Откройте [http://localhost:3000](http://localhost:3000).

Compose сначала ждёт готовности PostgreSQL, затем одноразовый сервис `migrate` применяет миграции; приложение запускается только после их успеха. Данные БД хранятся в volume `postgres_data`. `docker compose down` сохраняет данные; не добавляйте `--volumes`, если не хотите их удалить.

- `/` — главная страница.
- `/users` — пример текстового ответа.
- `/api/notes` — эталонный JSON API создания, чтения и удаления заметок; контракт задают `src/modules/notes/schemas.ts` и регистрации в `router.ts`.
- `/docs` — интерактивная документация Scalar с отправкой запросов.
- `/openapi.json` — сгенерированный OpenAPI-контракт подключённых API-модулей для Scalar и других клиентов.
- Неизвестный маршрут вне `/api` возвращает HTML 404; под `/api` — JSON Problem 404.

Исходники `src/`, тесты `tests/`, шаблоны `views/` и статика `public/` подключены с компьютера в контейнер read-only. Сгенерированный Prisma Client находится в отдельном volume `prisma_client` и обновляется перед запуском. Изменение TypeScript перезапускает сервер; изменения шаблонов и статики видны при следующем запросе. Локальный `node_modules` не попадает в контейнер.

После изменения зависимостей, Prisma-схемы или миграций, конфигурации проверок, README, правил команды или Dockerfile выполните `docker compose up --build` заново. `prisma/` копируется в образ, а не подключается с компьютера.

Полезные команды:

```sh
# Запуск в фоне с ожиданием готовности
# Перед этим остановите запуск в текущем терминале через Ctrl+C.
docker compose up --build --detach --wait

# Логи и состояние
docker compose logs --follow app
docker compose ps

# Полный verify без локальных Node.js и pnpm
docker compose run --rm app pnpm verify

# Остановка и удаление контейнеров проекта
docker compose down
```

## 5. Установить Node.js и pnpm — для локальной разработки

Этот раздел можно пропустить, если запускаете приложение только в Docker.

1. Установите **Node.js 24 LTS** с [nodejs.org](https://nodejs.org/), выбрав свою ОС и архитектуру. Вместе с Node.js устанавливается npm; он нужен только для первоначальной установки pnpm.
2. Заново откройте терминал и установите **pnpm 12.14.0**:

   ```sh
   npm install --global pnpm@12.14.0
   ```

3. Проверьте версии:

   ```sh
   node --version
   pnpm --version
   ```

Нужны Node.js версии 24 или новее и pnpm версии 12.14.0. Для одинакового окружения команды используйте Node.js 24 LTS; эта же основная версия используется в Dockerfile.

## 6. Запустить локально

```sh
pnpm install --frozen-lockfile
pnpm db:generate
docker compose up --detach --wait db
pnpm db:deploy
pnpm db:smoke
pnpm verify
pnpm dev
```

Для собственного PostgreSQL пропустите запуск сервиса `db` и задайте его URL. При смене `POSTGRES_HOST_PORT` обновите порт в локальном `DATABASE_URL`. Команды `db:deploy`, `db:migrate`, `db:studio`, `db:smoke` и `pnpm db ...` загружают `.env` через Node.js; не публикуйте настоящее содержимое файла.

Откройте [http://localhost:3000](http://localhost:3000). Не запускайте локальный сервер и Docker-сервер на одном порту одновременно.

`pnpm dev` запускает TypeScript средствами Node.js и автоматически перезапускает сервер после изменения импортируемых исходников. Этот режим **не проверяет типы** — перед передачей задачи или коммитом выполняйте `pnpm verify`. Конфигурация запрещает TypeScript-конструкции, которые нельзя выполнить встроенным механизмом Node.js без преобразования.

Сборка и запуск скомпилированного JavaScript:

```sh
pnpm build
pnpm start
```

Для production-режима дополнительно задайте переменную окружения `NODE_ENV=production` средствами вашей ОС или хостинга. Без неё Express использует development-режим.

Поэтому обычный `pnpm test` работает после установки зависимостей без ручной генерации и по-прежнему не загружает `.env`.

## Тесты: Vitest

```sh
# Все тесты один раз; этот режим использует CI
pnpm test

# Перезапуск тестов при изменениях
pnpm test:watch

# Только тесты конфигурации
pnpm test tests/config.test.ts
```

`vitest.config.ts` задаёт среду `node`, файлы `tests/**/*.test.ts`, изоляцию от env-файлов и запрет `.only`. HTTP-тесты отправляют реальные запросы на временный loopback-сервер без моков; серверы и соединения закрываются после каждого теста. Тесты конфигурации проверяют допустимые границы и отклонение некорректного ввода.

Vitest преобразует TypeScript для выполнения тестов, но обычный запуск **не проверяет типы**. Поэтому `pnpm check` отдельно запускает `tsc` для исходников, тестов и конфигурации Vitest, а `pnpm verify` сохраняет оба этапа. Само приложение по-прежнему запускается нативно в Node.js; Vite-сборка backend не добавлена.

## Схемы: Zod

`src/config.ts` экспортирует чистую `environmentSchema`, без чтения `process.env` или `.env` при импорте. `src/server.ts` валидирует окружение, использует типизированный числовой `PORT` и режим `NODE_ENV`, затем создаёт сервер. Посторонние переменные окружения не попадают в результат схемы. Zod — runtime-зависимость: проверка работает и в production-образе.

Для новых API определяйте схемы входов рядом с соответствующим модулем и используйте `safeParse` на границе приложения. В бизнес-логику передавайте только успешный `result.data`, а типы выводите через `z.infer<typeof schema>`, не дублируя их отдельными интерфейсами. HTTP-статус и формат ответа на ошибку сначала согласуйте в контракте задачи.

Zod проверяет конфигурацию сервера и входы эталонного Notes API. Общие HTTP-правила находятся в [API_CONVENTIONS.md](API_CONVENTIONS.md), точный контракт заметок — в `src/modules/notes/schemas.ts` и вызовах `api.register` в `router.ts`. Legacy-маршруты и HTML-ошибки вне `/api` сохранены.

## PostgreSQL и Prisma

`prisma/schema.prisma` описывает таблицы, `prisma/migrations/` хранит SQL-миграции. Модель `Note` используется эталонным API и командой `pnpm db:smoke`. Эта команда создаёт запись, проверяет сохранённые поля и удаляет её в одной транзакции. Существующие `/` и `/users` не обращаются к БД.

`src/database.ts` экспортирует фабрику без подключения при импорте. `src/server.ts` создаёт один клиент с PostgreSQL-адаптером и пулом на процесс, проверяет БД реальным SQL-запросом, затем передаёт клиент в `createApp(db)`. Фабрика приложения внедряет его в маршруты; `app.locals` для доступа к БД не используется. Не создавайте клиент для каждого запроса. Импорт модулей не открывает порт и не подключается к БД.

Получение соединения из пула ограничено 5 секундами, чтобы недоступная БД не оставляла запуск в бесконечном ожидании. При ошибке подключения сервер завершает работу без вывода URL и пароля.

`prisma.config.ts` использует ту же Zod-схему для URL. Генерация и проверка схемы допускают отсутствие URL, миграции и Studio требуют настроенного подключения. Клиент генерируется в `src/generated/prisma/`, не коммитится, использует ESM и `.ts`-импорты; `tsc` компилирует его вместе с приложением. Не редактируйте сгенерированные файлы.

Порядок изменения модели:

1. Согласуйте таблицы и связи; назначьте одного ответственного за интеграцию миграций.
2. Измените `prisma/schema.prisma`.
3. На своей dev-базе выполните `pnpm db:migrate --name descriptive_name`, затем `pnpm db:generate`.
4. Проверьте SQL, закоммитьте схему и миграцию, выполните `pnpm verify` и `pnpm db:smoke`.
5. Остальные участники применяют готовые миграции через `pnpm db:deploy`. Не используйте `db push` вместо истории миграций и не запускайте `migrate reset` на чужих данных.

`migrate dev` требует права создавать shadow database. В production применяйте только готовые миграции отдельным шагом до запуска приложения. Обычный `pnpm verify` и CI не требуют PostgreSQL и не подгружают `.env`; проверку реальной БД запускайте отдельно.

## Эталонный модуль и реальная HTTP-проверка

`src/modules/notes/` содержит API-модуль с внедрённой БД, строгие Zod-схемы и регистрации операций для Express и OpenAPI. Это небольшой публичный учебный пример без авторизации; не записывайте чувствительные данные и не считайте его готовой системой разграничения доступа.

- `POST /api/notes` с JSON `{ "content": "Заметка" }` → `201`, объект `{ id, content, createdAt }` и `Location`.
- `GET /api/notes/{id}` → `200` с объектом либо `404`.
- `DELETE /api/notes/{id}` → `204` без тела либо `404`.
- Неверный ввод → `400`, неподдерживаемый формат → `415`, JSON больше 16 KiB → `413`. Все ошибки `/api` — `application/problem+json`; неизвестные ошибки не раскрывают SQL, stack trace или секреты.

`content` обрезается по краям и должен содержать 1–2000 Unicode code points: например, один emoji считается одним символом, а базовая буква с отдельным комбинируемым знаком — двумя. Это фактическое поведение Zod-схемы, не длина UTF-16 строки JavaScript. Неизвестные поля и query-параметры запрещены. Список и обновление не реализованы и не обещаются этим контрактом.

После запуска своей PostgreSQL и применения миграций:

```sh
pnpm api:smoke
```

Команда запускает своё приложение на временном loopback-порту, выполняет реальные HTTP-запросы создания, чтения и удаления, проверяет `Location`, нормализацию и верхнюю границу длины, отсутствие удалённой записи, повторное удаление и невалидный ввод. В конце закрывает сервер/БД и удаляет только собственную запись с уникальным маркером, в том числе при ошибке.

В Docker после `docker compose up --build --detach --wait`:

```sh
docker compose exec app pnpm api:smoke
```

`tests/notes.test.ts` и `tests/http.test.ts` проверяют настоящим HTTP входные границы и ошибки до SQL, без внешней БД и без моков. Они входят в обычный `pnpm verify`; успешную работу с PostgreSQL доказывает отдельный `api:smoke`. Общие HTTP test helpers находятся в `tests/helpers/http.ts`, принадлежат интегратору и не копируются в каждый модуль.

## Интерактивная документация Scalar

После запуска приложения откройте [http://localhost:3000/docs](http://localhost:3000/docs). При другом HTTP-порте используйте тот же адрес приложения с путём `/docs`.

Scalar отображает сгенерированный `/openapi.json`: схемы запросов/ответов, ошибки и кнопки **Test Request** для отправки настоящих запросов в это же приложение. Источник контракта — Zod-схемы в `schemas.ts` и `api.register` в API-модуле: один вызов связывает HTTP-метод, полный путь, описание входов/ответов и обработчик с Express и реестром OpenAPI. Запросы из документации действительно меняют данные; для экспериментов используйте свою dev-БД.

Документ OpenAPI 3.1 генерируется один раз при сборке приложения в `createApp(db)` из единственного массива активных `apiModules`. `pnpm build` выполняет генерацию Prisma Client и `tsc`, без копирования контракта; тот же механизм работает через `pnpm start` и в production-образе. Не редактируйте и не коммитьте статическую сгенерированную спецификацию: проверяйте JSON через HTTP-тесты или Scalar. Старый `/openapi.yaml` намеренно удалён без совместимого alias; бизнес-endpoints не изменились.

Чтобы добавить endpoint в свой модуль, объявите схемы в `schemas.ts`, используйте их же в `safeParse` обработчика и в `api.register` с полным путём `/api/<resource>/{id}`. Пошаговый пример — в [API_CONVENTIONS.md](API_CONVENTIONS.md). Описания, примеры, заголовки и статусы ошибок автор задаёт явно; генератор не угадывает произвольный Express-код, не валидирует запросы или ответы за обработчик и не читает второй контракт из JSDoc или YAML. Новые бизнес-маршруты нельзя добавлять через обходящий реестр `router.get/post`.

Используется официальный `@scalar/express-api-reference` **0.10.31** и закреплённый браузерный renderer **1.76.0** из jsDelivr. Для загрузки интерфейса браузеру нужен доступ к CDN; это не автономный offline-интерфейс. Телеметрия и загрузка шрифтов Scalar отключены, отдельный CORS proxy не подключён. В devDependencies добавлен `@types/har-format`: декларации текущего Scalar импортируют эти типы, но не устанавливают их транзитивно; строгая проверка типов не отключалась.

В интерфейсе оставлены документация и ручная отправка HTTP-запросов; дополнительные панели и рекламные кнопки отключены.

`/docs` и `/openapi.json` доступны без авторизации, как и учебный Notes API. Не включайте секреты в OpenAPI-примеры и не считайте документацию механизмом защиты API. Captain владеет общим registrar/generator и подключением фабрики модуля в `createApp`; владелец модуля — схемами, метаданными операций и тестами. Все регистрации уже подключённого модуля попадают в документацию автоматически; отдельного списка для документации и автопоиска неподключённых модулей нет.

## Структура

- `src/app.ts` — фабрика `createApp(db)`, подключение модулей и раздельные API/HTML-ошибки.
- `src/server.ts` — запуск HTTP-сервера; порт задаётся через `PORT`, по умолчанию 3000.
- `src/config.ts` — Zod-схема конфигурации без побочных эффектов.
- `src/database.ts` — создание Prisma Client с PostgreSQL-адаптером.
- `prisma/` — схема и история миграций.
- `prisma.config.ts` — конфигурация CLI.
- `scripts/database-smoke.ts` — реальная проверка БД.
- `src/modules/notes/` — эталонный JSON API: регистрации операций и общие для runtime/OpenAPI Zod-схемы.
- `src/http/problem.ts` — общий обработчик ошибок API.
- `scripts/notes-smoke.ts` — HTTP-проверка Notes с настоящим PostgreSQL.
- `src/http/openapi.ts` — общий registrar Express/OpenAPI и генерация документа.
- `src/routes/` — legacy-маршруты приложения.
- `tests/` — тесты Vitest для HTTP и конфигурации.
- `views/` — шаблоны Pug.
- `public/` — статические файлы.
- `dist/` — результат сборки; не коммитится.

Проект использует `pnpm-lock.yaml`. Для зависимостей используйте pnpm, а не `npm install`. Локальный `pnpm-workspace.yaml` выделяет приложение в отдельный workspace и отключает установочные скрипты зависимостей (`ignoreScripts: true`). Не используйте `--ignore-workspace`: этот флаг отключает локальную конфигурацию.

## Production-образ

Docker Compose предназначен для разработки. Отдельный финальный stage Dockerfile содержит скомпилированный JavaScript, шаблоны, статику и только production-зависимости; сервер запускается не от root.

```sh
docker build --target production --tag express-app .
# DATABASE_URL уже должен быть задан в окружении; миграции примените отдельно.
docker run --rm --init --env DATABASE_URL --publish 3000:3000 express-app
```

Финальный образ не содержит `.env` и запускает Node.js напрямую. В production передавайте конфигурацию переменными окружения хостинга или параметрами Docker; не встраивайте секреты в образ. Не передавайте разработческий `.env` с `NODE_ENV=development` в production без явного переопределения режима.

Перед запуском production-образа примените `pnpm db:deploy` из checkout с установленными dev-зависимостями, направив его на целевую БД. Финальный образ не содержит Prisma CLI и не создаёт/обновляет таблицы при старте. URL из `.env.example` с `127.0.0.1` не указывает на БД хоста из контейнера: задайте доступный из контейнера адрес.

## Командная работа и CI

- Обязательная конвенция API: [API_CONVENTIONS.md](API_CONVENTIONS.md); владение файлами, worktree/БД/порты и порядок небольших PR: [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md).
- Шаблон задачи: [.github/ISSUE_TEMPLATE/task.yml](.github/ISSUE_TEMPLATE/task.yml). Перед началом работы заполните цель, границы, контракт и проверяемые критерии приёмки.
- Шаблон PR: [.github/pull_request_template.md](.github/pull_request_template.md). Укажите фактический результат verify и ручного smoke, не только список изменённых файлов.
- Одна задача — одна ветка и один исполнитель. Изменения общих контрактов, зависимостей, env и проверок согласуются с тимлидом.

GitHub Actions workflow `CI` запускает проверку `verify` на pull request, push в `main` и вручную. Он использует Node.js 24, pnpm 12.14.0, установку по lockfile с отключёнными install scripts и ту же команду `pnpm verify`. Workflow не использует секреты и имеет только read-only доступ к содержимому репозитория. Проверки должны проходить без личного `.env`.

После публикации проекта в GitHub и первого запуска CI владелец репозитория должен настроить Ruleset / branch protection для `main`:

1. Запретить прямые изменения: принимать их только через PR.
2. Требовать успешную status check `verify` из workflow `CI`.
3. Требовать минимум одно человеческое одобрение, сбрасывать устаревшие одобрения после новых коммитов и требовать закрытия обсуждений.
4. Запретить force push и удаление ветки, ограничить обход правил, в том числе привилегированными участниками, насколько позволяет тариф хостинга.

Файлы стартера **не включают branch protection автоматически** и не гарантируют ревью именно тимлидом. Настройки GitHub необходимо применить отдельно.

## Проверка перед хакатоном

Каждый участник должен заранее:

1. Проверить доступ к репозиторию и возможность сделать коммит под своим именем.
2. Из свежего клона запустить один из двух вариантов и открыть `/` и `/users`.
3. Изменить исходник и убедиться, что сервер перезапустился.
4. Выполнить полный `pnpm verify` локально или внутри Docker.

Первая сборка скачивает образ и зависимости. Запуск заранее прогреет кеши, но не гарантирует полностью автономную работу при будущих изменениях зависимостей.
