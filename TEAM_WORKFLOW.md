# Работа команды

Обязательны [API_CONVENTIONS.md](API_CONVENTIONS.md). Документы — инструкции, а не техническая блокировка: review и GitHub branch protections владелец репозитория настраивает отдельно.

## Владение до начала работы

Первоначальный **captain — владелец репозитория**; в существующих правилах и шаблонах «тимлид» обозначает эту же роль согласования. Он может явно передать роль реальному участнику, записав решение в Issue. Роли можно совмещать; четыре участника не означают четыре обязательные должности.

- Captain владеет `src/app.ts`, `src/server.ts`, `src/database.ts`, `src/config.ts`, `src/http/**` (включая общий registrar/generator OpenAPI), общими test helpers, конфигурацией, `prisma/schema.prisma` и интеграцией миграций, `package.json`, lockfile, build/Docker/Compose/CI и общими правилами. Он интегрирует фабрики модулей в единственный массив `apiModules` в `createApp`: отдельного списка документации нет.
- Владелец модуля — **один реальный Issue Assignee**, назначенный до работы. В Issue укажите модуль, точные разрешённые файлы и отдельные файлы тестов. Он меняет свой `src/modules/<module>/**`, включая `schemas.ts` и метаданные операций `api.register` в `router.ts`, и свои тесты/скрипты. Notes — существующий образец, не разрешение придумывать новые продуктовые модули.
- Нет назначения или пересекаются границы — сначала captain уточняет Issue. Не угадывайте владельца и не редактируйте общий файл одновременно. Запрос подключения фабрики API-модуля, общего helper или изменения схемы оставьте в Issue: файл, требуемый интерфейс, контракт и зависимая задача. Captain выполняет интеграцию либо явно передаёт исключительное владение на время изменения.

## Одна задача — одна ветка и worktree

Небольшой PR решает один законченный сценарий. Сначала согласуйте контракт и границы, затем работайте параллельно только в непересекающихся файлах. Отдельный worktree не изолирует БД, порты и Docker сам по себе.

Пример для задачи №123; выполняется человеком из основного checkout. Для другой задачи замените номер в ветке, каталоге и Compose project, выберите свободные HTTP/DB-порты и согласуйте их с командой. Команды ниже — инструкция, не отчёт о выполнении.

```sh
git fetch origin
git worktree add -b task/123-notes ../express-app-123 origin/main
cd ../express-app-123
pnpm install --frozen-lockfile
export COMPOSE_PROJECT_NAME=express_app_123
export HOST_PORT=3123
export PORT=3123
export POSTGRES_HOST_PORT=55123
export DATABASE_URL=postgresql://express:express@127.0.0.1:55123/express_app
pnpm db:generate
docker compose up -d --wait db
pnpm db:deploy
pnpm dev
```

Node.js и версия pnpm должны соответствовать `package.json`. Здесь приложение работает на хосте: HTTP `http://127.0.0.1:3123`, PostgreSQL — отдельный Compose volume проекта `express_app_123`, URL совпадает с опубликованным портом `55123`. У других участников должны отличаться Compose project и оба host-порта; одинаковое имя БД внутри разных контейнеров безопасно. Логин/пароль выше — публичный локальный пример из Compose, не production credentials. При запуске всего Compose через `docker compose up --build` приложение внутри контейнера использует уже заданный в Compose URL `db:5432`; не переносите его в URL хостового процесса.

`.env` не копируется `git worktree`. Не копируйте чужой `.env` и не публикуйте реальные секреты. Для этого примера достаточно явных безопасных переменных выше; для остальных настроек сверяйтесь с `.env.example`. Не направляйте разработку и smoke в общую или production БД. После работы остановите свой dev-процесс и выполните `docker compose down` из своего worktree с тем же `COMPOSE_PROJECT_NAME`; не удаляйте чужие volumes.

## Схема, зависимости и конфликты

- Изменения общей схемы captain интегрирует **до** зависимых features. Зависимая ветка обновляется после интеграции и генерирует клиент заново. Не меняйте схему в параллельных модульных PR без согласования.
- Не удаляйте и не переписывайте уже применённые миграции: исправление — новая согласованная миграция. Не сливайте вручную generated snapshots/Prisma client; пересоздайте их штатной генерацией. Сгенерированный Prisma client игнорируется Git.
- Зависимости и lockfile меняет captain через package manager после одобрения; lockfile не редактируется вручную. Не меняйте env, build, Docker, CI и проверки ради обхода ошибки.
- Конфликт решается по согласованному контракту и владельцем затронутой области, а не произвольным выбором «ours/theirs». При изменении контракта обновите Issue, реализацию, Zod-схемы, метаданные `api.register` и тесты вместе. Сгенерированный `/openapi.json` проверяйте через HTTP или Scalar, но не редактируйте и не коммитьте как статический файл.
- Не форматируйте весь репозиторий из модульной ветки. Не включайте чужие изменения или несвязанные рефакторинги в PR.

## Интеграция и merge

1. Исполнитель заканчивает свой модуль, контракт и отдельные тесты, фиксирует изменения и запрашивает общую интеграцию у captain в Issue. Остальные участники не запускают проверки на полусобранном общем дереве.
2. Перед merge обновите ветку от актуального `origin/main` по принятому командой способу, разрешите конфликты с владельцами и заново сгенерируйте клиент при изменении схемы. Не переписывайте чужую опубликованную историю без согласования.
3. Назначенный интегратор один раз на итоговом дереве выполняет полный `pnpm verify` и реальный smoke: legacy `/`, `/users`, `/stylesheets/style.css`, неизвестный legacy URL, неизвестный `/api` URL и изменённый API-сценарий. Для Notes нужен отдельный smoke создания/чтения/удаления с настоящим PostgreSQL по README. Изолированные HTTP-тесты не заменяют его.
4. В PR запишите фактические команды, результаты и статусы smoke, изменения OpenAPI, миграции и согласования. Невыполненное явно пометьте, не заявляйте успех. Требуются человеческое review и одобрение captain для общих границ; merge только после устранения сбоев и принятия критериев задачи.
